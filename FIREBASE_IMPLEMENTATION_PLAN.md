## 3. Firestore Database Design (Objective B)

### 3.1 Collection Overview

```
firestore/
├── users/{userId}                    # PRIMARY — User profiles (extends Firebase Auth)
├── buildings/{buildingId}            # Campus buildings (from GeoJSON + admin edits)
├── pathways/{pathwayId}              # Campus pathways (from GeoJSON + admin edits)
├── campus_boundary/main              # Single document — campus boundary polygon
├── evacuation_graphs/{graphId}       # Versioned evacuation graphs (nodes + edges)
├── alerts/{alertId}                  # Emergency alerts (real-time listeners)
├── emergency_reports/{reportId}      # User-submitted emergency reports
├── audit_logs/{logId}                # Immutable audit trail (admin-only read)
├── fcm_tokens/{userId}               # FCM token → user mapping (for server sends)
├── settings/{settingId}              # App-wide settings (admin configurable)
└── analytics/{date}_daily            # Aggregated analytics (Function-written)
```

**Design Decisions:**

1. **`users` not `user_profiles`** — Single collection, document ID = Firebase Auth UID. Avoids duplicate collections.
2. **No separate `roles` collection** — Role stored as field in `users` + Custom Claims for security rules.
3. **`campus_boundary` as single doc** — One boundary per campus; use subcollection if multi-campus later.
4. **`evacuation_graphs` versioned** — Full graph per document; version field for history.
5. **`fcm_tokens` separate from users** — Allows multiple tokens per user (multi-device), TTL cleanup.
6. **`audit_logs` write-only for clients** — Only Cloud Functions (Admin SDK) can write.

## 4. Firestore Security Rules Design (Objective C)

### 4.1 Helper Functions

```javascript
// firestore.rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // ============ HELPER FUNCTIONS ============
    function isAuthenticated() {
      return request.auth != null;
    }
    
    function isOwner(uid) {
      return isAuthenticated() && request.auth.uid == uid;
    }
    
    function getUserRole() {
      return isAuthenticated() ? request.auth.token.role : null;
    }
    
    function hasRole(roles) {
      return isAuthenticated() && request.auth.token.role in roles;
    }
    
    function isAdmin() {
      return hasRole(['admin']);
    }
    
    function isSecurity() {
      return hasRole(['security']);
    }
    
    function isAdminOrSecurity() {
      return isAdmin() || isSecurity();
    }
    
    function isFacultyOrAdmin() {
      return hasRole(['faculty', 'admin']);
    }
    
    function isActiveUser() {
      return isAuthenticated() && 
        (get(/databases/$(database)/documents/users/$(request.auth.uid)).data.isActive == true);
    }
    
    // Validate user document structure on create
    function validUserCreateData() {
      let allowedKeys = [
        'email', 'firstName', 'lastName', 'middleInitial', 'role',
        'studentId', 'employeeId', 'department', 'phoneNumber',
        'isActive', 'emailVerified', 'createdAt', 'updatedAt',
        'language', 'notificationPrefs', 'emergencyContactName',
        'emergencyContactPhone'
      ];
      return request.resource.data.keys().hasOnly(allowedKeys);
    }
    
    // Validate user document updates (owner)
    function validUserOwnerUpdate() {
      let allowedKeys = [
        'firstName', 'lastName', 'middleInitial', 'phoneNumber',
        'photoUrl', 'emergencyContactName', 'emergencyContactPhone',
        'language', 'notificationPrefs', 'fcmToken', 'lastLoginAt', 'updatedAt'
      ];
      return request.resource.data.diff(resource.data).affectedKeys().hasOnly(allowedKeys);
    }
    
    // Validate user document updates (admin)
    function validUserAdminUpdate() {
      let allowedKeys = [
        'firstName', 'lastName', 'middleInitial', 'phoneNumber',
        'photoUrl', 'emergencyContactName', 'emergencyContactPhone',
        'language', 'notificationPrefs', 'fcmToken', 'lastLoginAt', 'updatedAt',
        'role', 'isActive', 'studentId', 'employeeId', 'department'
      ];
      return request.resource.data.diff(resource.data).affectedKeys().hasOnly(allowedKeys);
    }
    
    // ============ COLLECTION RULES ============
```

### 4.2 Collection Rules

#### 4.2.1 `users/{userId}`

```javascript
    match /users/{userId} {
      // Read: Owner, Admin, Security
      allow read: if isOwner(userId) || isAdminOrSecurity();
      
      // Create: Only on auth signup (owner), with validated fields
      allow create: if isOwner(userId) 
        && validUserCreateData()
        && request.resource.data.email == request.auth.token.email
        && request.resource.data.isActive == true
        && request.resource.data.emailVerified == false;
      
      // Update: Owner (limited fields) or Admin (all fields)
```

## 5. Cloud Functions Design (Objective D)

### 5.1 Why Server-Side (Cloud Functions) vs Client-Side

| Operation | Must Be Server-Side | Reason |
|-----------|---------------------|--------|
| **Set Custom Claims (roles)** | ✅ Yes | Requires Admin SDK; clients cannot self-assign roles |
| **Send FCM to topics** | ✅ Yes | Topic management + send requires Admin SDK; prevents spam |
| **Validate emergency reports** | ✅ Yes | Rate limiting, priority calculation, auto-escalation |
| **Create audit logs** | ✅ Yes | Immutable, tamper-proof; client cannot be trusted |
| **Aggregate analytics** | ✅ Yes | Expensive reads; run once daily via scheduled function |
| **Cleanup expired tokens/alerts** | ✅ Yes | Scheduled maintenance; clients may be offline |
| **Bulk import campus data** | ✅ Yes | Large writes; Admin SDK bypasses rules safely |
| **User role changes** | ✅ Yes | Must sync Custom Claims + Firestore atomically |

| Operation | Can Be Client-Side | Reason |
|-----------|-------------------|--------|
| **User profile CRUD** | ✅ | Owned by user; security rules enforce |
| **Read buildings/pathways** | ✅ | Public read; offline sync via Firestore |
| **Submit emergency report** | ✅ | User creates own doc; Function processes |
| **Acknowledge alert** | ✅ | User adds self to array; rules allow |
| **Read evacuation graphs** | ✅ | Public read; real-time updates via listeners |

#### 5.3.5 `registerToken` (Callable - Client)

```typescript
// Callable: httpsCallable('registerToken')
export const registerToken = functions.https.onCall(async (data, context) => {
  if (!context.auth) {
    throw new functions.https.HttpsError('unauthenticated', 'Sign in required');
  }
  
  const { token, platform, appVersion } = data;
  const uid = context.auth.uid;
  
  // Validate token format (basic)
  if (!token || token.length < 100) {
    throw new functions.https.HttpsError('invalid-argument', 'Invalid FCM token');
  }
  
  const tokenRef = admin.firestore().collection('fcm_tokens').doc(uid);
  
  await admin.firestore().runTransaction(async (transaction) => {
    const doc = await transaction.get(tokenRef);
    const tokens = doc.exists ? doc.data()?.tokens || {} : {};
    
    tokens[token] = {
      platform,
      appVersion,
      lastUsed: FieldValue.serverTimestamp(),
      isActive: true
    };
    
    // Keep only last 5 tokens per user
    const sortedTokens = Object.entries(tokens)
      .sort((a, b) => b[1].lastUsed - a[1].lastUsed)
      .slice(0, 5);
    
    transaction.set(tokenRef, { 
      tokens: Object.fromEntries(sortedTokens),
      updatedAt: FieldValue.serverTimestamp()
    }, { merge: true });
  });
  
  return { success: true };
});
```

### 7.3 Cost Optimization Strategies

3. **TTL Indexes** — Auto-delete expired alerts, old tokens, stale reports
4. **Aggregate via Functions** — Daily analytics written once, not queried per-user
5. **Limit Listeners** — Use `limit()` and `where()` to minimize document reads
6. **Cache FCM Topics** — Functions cache topic mappings in memory

| Requirement | Status | Action |

| **Node.js 20+** | Required for Functions | Verify locally |

| **Staging Project** | Recommended | Create `safenav-cavite-staging` |

### 7.5 FCM Considerations

- **FCM is free** — No cost for messages
- **Topic limits:** 1000 topics per app, unlimited subscriptions
- **Message size:** 4KB data payload, 2KB notification payload
- **Delivery:** Best-effort; not guaranteed for critical alerts
- **iOS Critical Alerts:** Requires Apple entitlement + special FCM payload
- **Fallback:** Local notifications (already implemented) for foreground/offline

### 7.6 Storage Considerations

- **Profile photos:** Resize to max 512x512 before upload (~50KB each)
- **Alert attachments:** Limit to 5MB each, max 5 per alert
- **Evacuation maps:** Store as GeoJSON in Firestore (small), not Storage
- **Lifecycle rules:** Auto-delete files > 1 year in `alert_attachments/`
