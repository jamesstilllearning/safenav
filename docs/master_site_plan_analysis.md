# EARIST Cavite Master Site Plan Analysis

## Project and scope

This analysis supports SAFENAV CAVITE, a Flutter campus navigation and emergency evacuation system for EARIST Cavite Campus. The supplied project image, **EARIST CAVITE Master Site.png**, is treated as the primary visual reference for names and relative layout. Existing application data was inspected only to assess integration; the image is not treated as a source of geographic coordinates.

The source image is a 2048 × 1391 pixel photograph/scan titled **MASTER SITE DEVELOPMENT PLAN**. It is perspective-distorted, has glare and low-contrast areas, and has no visible scale bar, coordinate grid, georeferencing information, or legible plan revision/date. Its labels and project-status colors describe what the plan depicts, not necessarily current campus conditions.

## Spatial and pedestrian-connectivity assessment

- The plan places a concentration of proposed uses along its upper and eastern edges, with existing academic, clinic, training, and service labels across the western and central areas.
- The EXISTING QUADRANGLE and EXISTING MAIN BUILDING HALL occupy the lower/central portion; the Hall is drawn along the Congressional Road frontage.
- The Creek is labelled beyond the upper/right edge. The master plan shows no named bridge or crossing.
- The existing main gate and proposed secondary access gate are both shown at the road-facing lower edge. Their present operation, accessibility, and hours are not established by the image.
- Proposed road access and proposed pathwalk corridors are visible around multiple footprints. Proximity and touching colored shapes do not prove walkable connection, public access, or a continuous route.
- The plan has no readable entrance symbols, accessible-route markings, widths, ramps, stairs, surface specifications, one-way rules, restricted-area markers, or path closure status.
- Several leader lines cross the plan, and glare obscures portions of the drawing. For the northern/eastern callouts, exact callout-to-footprint matches are not consistently certain.

Accordingly, this image supports qualitative layout relationships and candidate graph locations only. It does not support a verified pedestrian graph or route geometry.

## Potential evacuation destinations

There is no visible label, symbol, or legend item designating an evacuation area, assembly point, emergency shelter, or official evacuation route. The Existing Quadrangle and Proposed grass quadrangle are visible open spaces that could be evaluated by campus emergency officials, but neither may be called an official evacuation destination based on this source. Any evacuation routing also needs approved hazard information, capacity, accessibility, operating rules, and current exit status.

## Flutter architecture compatibility assessment

### Existing map and assets

- The app already uses **flutter_map** with OpenStreetMap tiles, cached/offline tile support, panning, and zooming (map zoom limits 10–20). Rotation is disabled.
- The map screen overlays campus boundary, building polygons, pathway lines, user location, selected-feature UI, and an active route polyline.
- Static map assets are GeoJSON under lib/src/features/map/data and are declared individually in pubspec.yaml.
- Existing CampusBuilding requires an OSM way ID, geospatial polygon, centroid, and other map metadata. CampusPathway and CampusBoundary also use latitude/longitude geometry.
- Current campus_buildings.geojson contains four generically named features (“EARIST Cavite Building 1” through “Building 4”); campus_pathways.geojson contains 11 named features. Their metadata says OpenStreetMap, but those generated-looking names and statuses are not labels from the supplied master plan. They must not override the plan's official labels without separate verification.
- The supplied plan has no geographic coordinates or scale. It cannot be placed accurately on the existing geographic map or used to populate latitude/longitude centroids from visual estimates.

### Markers, search, and directory

Building polygons are rendered from the loaded building dataset and can be selected. The map selection panel displays a building name and has a route action. Navigation search filters the loaded building names and returns destinations using each building's centroid. This provides a usable foundation, but the present data names do not match the official labels in the master plan. Search results and markers will only be authoritative once each plan label is linked to an approved footprint and coordinate source. A separate directory screen is not evident in the inspected map/navigation flow.

### Navigation graph and Dijkstra

NavigationService already builds a graph from pathway coordinate sequences and computes shortest routes with Dijkstra. Edges hold distance, pathway ID, category, and geometry; building destinations are connected to the nearest pathway node. The current graph builder merges points within 5 metres and attaches a building to the nearest path node within 50 metres. Those proximity rules can create inferred connections that the site plan does not prove.

The current edge model has no explicit verified/inferred evidence state, access restriction, closure, accessibility, direction, or hazard fields. The current navigation provider calls the route function with avoidEmergencyPaths enabled; that behavior is not an evacuation-routing policy and should not be reused as one without review. A site-plan transcription must not be converted directly into the current graph.

For a later Dijkstra integration, use approved graph nodes for entrances, gates, path junctions, and destinations; edges should store surveyed geometry, positive travel cost, source, verification state, accessibility/restriction/closure status, and any approved hazard cost. Connect buildings only to a confirmed entrance and path junction. Exclude closed or restricted edges; support accessibility preferences and a separately approved evacuation mode.

### Firebase and data loading

Firebase Core/Auth/Firestore are configured, and the inspected Firestore service handles user profiles. The campus map data path currently loads local bundled GeoJSON; no Firestore-backed building/pathway source was found in the inspected map flow. Keeping the reviewed campus reference dataset as a versioned local asset fits the current architecture. The requested assets/data/campus_buildings.json path does not yet appear in pubspec.yaml and will need a deliberate loader/asset registration if implementation is later approved.

## Recommended integration approach

1. Preserve this transcription as the plan-reference layer and retain exact source labels, project status wording, confidence, and notes.
2. Obtain the current official georeferenced CAD/GIS/PDF or surveyed campus data, plus the plan revision date. Confirm spelling, current building existence, proposed-project completion, and which annotations refer to distinct footprints.
3. Have campus staff validate entrances, paths, gate operation, restricted areas, accessible routes, surface/grade details, and temporary closures.
4. Ask the campus safety authority to identify official assembly points, evacuation exits/routes, hazard zones, capacity, and policy. Do not derive these from open-space coloring.
5. Once authoritative geometry is available, map each provisional ID to a verified footprint and entrance; keep site-plan names and geospatial geometry traceable to their respective sources.
6. Integrate through the existing map data/provider layer and adapt the current model or add a source-aware record type. The plan-only records cannot satisfy the current required OSM IDs, polygons, or centroids on their own.
7. Build the navigation graph from validated path centerlines and explicit junctions. Preserve distinctions between confirmed, proposed, inferred, closed, and restricted edges. Do not enable routing on proposed paths until their existence and access are verified.
8. Only after the report is reviewed and the user authorizes implementation should the Flutter assets, loader, markers, directory, search, or routing code be changed.

## Uncertainties and confirmations needed

- The plan revision/date and current state of all “proposed,” “on-going,” and “recently accomplished” items are not legible.
- The staff-housing label is clipped at the right image boundary; its final character(s) cannot be transcribed from this PNG. The eastern multipurpose label is also clipped, but a separate complete callout has identical wording.
- One interior plantation label is partly obscured and may read “PROPOSED red fox dragon plantation.”
- The proposed northern/eastern callout leaders do not always identify a unique footprint at this image quality.
- Some repair/construction callouts may refer to parts of the Main Building Hall or another existing facility, not separate buildings.
- The campus boundary, building geometries, entrances, path geometry, coordinates, lengths, and connectivity require authoritative geospatial data or a field survey.
- No evacuation destination or route is designated in the image.
- Existing GeoJSON labels and route names are not confirmed against this master plan.
