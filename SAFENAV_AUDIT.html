Executive summary

SAFENAV CAVITE has solid design-system bones: a Material 3 theme system (lib/src/core/theme/app_theme.dart), a comprehensive shared widget library (lib/src/shared/widgets/), and a go_router + flutter_riverpod architecture built around a 5-tab bottom-nav shell (Map, Navigate, Emergency, Alerts, Profile) with a Begin entry screen replacing login.

The app is incomplete and inconsistent. Several screens are TODOs or placeholders, the router references screens that do not exist, duplicated helper logic appears across files, and accessibility/responsiveness are unevenly implemented. The strongest assets are the shared widget library and theme system — both are reusable and well-typed. The weakest area is the profile feature (~5,838 inline lines, mostly stubbed), followed by missing router routes and duplicated severity/color/instruction-icon switch functions.

Core recommendation: Do not start by redesigning individual screens. Lock down the shared design system first (theme tokens, component library, navigation patterns, bottom sheets, empty/error/loading states), then bring each screen up to that standard one at a time.

Preservation constraints honored: This is a read-only audit. No files were created, modified, deleted, renamed, or moved. Firebase config, Firestore rules, navigation algorithms, routing logic, campus map SVGs, navigation graph JSON, node/edge IDs, and coordinates were not touched. Authentication was not reintroduced. No new features were implemented.

Per-screen UI/UX assessment

Each assessment distinguishes visual, layout, interaction, functional, and backend-dependent concerns.

BeginScreen — entry (replaces login)

lib/src/features/onboarding/presentation/screens/begin_screen.dart

  • Visual: Large AppFilledButton "BEGIN" → AppRoutes.home. Clean, minimal, appropriate entry point.
  • Layout: Centered, single primary action; good use of space.
  • Interaction: One clear call-to-action; no sign-up/sign-in noise.
  • Functional: Correctly replaces the removed login system.
  • Accessibility: Button supports semanticLabel via AppFilledButton.
  • Assessment: Strong — this is the pattern the rest of the app should follow.

MapScreen — home tab

lib/src/features/map/presentation/screens/map_screen.dart

  • Visual: flutter_map with indoor/outdoor modes, building/pathway/room/marker/polyline layers. Map-first design is correct for this app.
  • Layout: Full-screen map with bottom sheets, toolbar, zoom controls, selection info bar, FAB, indoor floor selector. Dense but map-centric.
  • Interaction: Six bottom sheet types for different feature types; building selector; layer options; floor selector.
  • Functional: Backend-dependent (map tiles, building data, graph). Indoor floor switching is a key differentiator.
  • Accessibility: Map markers have no screen-reader alternative; bottom sheets need explicit semantic labels.
  • Responsiveness: DraggableScrollableSheet adapts to screen height; FAB may collide with bottom nav on small phones.
  • Assessment: Good map-first foundation; six sheet types create UI fragmentation.

NavigationScreen — navigate tab

lib/src/features/navigation/presentation/screens/navigation_screen.dart

  • Visual: State machine (Idle/Initializing/Ready/Active/Error). DestinationSearchBar, RoutePreviewBar, RoutePreviewCard, CommonDestinationsList, quick action cards, stat chips.
  • Layout: Search bar at top; common destinations horizontal scroll; route preview bar/card. Information-dense.
  • Interaction: Start-location mode selector (GPS/Indoor/Outdoor); destination search; saved routes sheet. Voice search stubbed ("coming soon").
  • Functional: Haversine distance helpers inline; duplicated in destination_details_bottom_sheet.dart; imperative Riverpod provider usage.
  • Assessment: Functional core, but duplicated helpers and stubbed voice guidance are liabilities.

EmergencyScreen

lib/src/features/emergency/presentation/screens/emergency_screen.dart

  • Visual: 3-second SOS hold via Timer + AnimationController pulse + progress ring; confirmation dialog; Fire/Medical/Security quick actions; emergency red theme.
  • Layout: Full-screen status view with PopScope canPop:false; timeline, responder info, cancel dialog.
  • Interaction: Long-press SOS hold is correct for preventing accidental triggers; confirmation dialog adds safety.
  • Functional: Firestore emergency contacts; assembly point & evacuation route cards. Critical issue: _activateSos requires userId and shows "Please log in" despite the app having no login.
  • Accessibility: SOS hold needs haptic/audio fallback; progress ring needs a text equivalent.
  • Assessment: Strong interaction design; the login contradiction is a functional bug that blocks launch.

AlertsScreen

lib/src/features/alerts/presentation/screens/alerts_screen.dart

  • Visual: TabBar (All/Unread/Critical); _AlertTile, AlertDetailScreen, CreateAlertScreen, related-alerts section; filter chips.
  • Layout: List-based standard alert pattern; FCM init/registerToken; Firestore stream providers.
  • Interaction: FilterParams equality/hashCode implemented. Severity/color switch functions duplicated in 3 places.
  • Functional: Real-time Firestore stream; unread-count stream; critical filtering. Create alert is admin/security only (placeholder).
  • Accessibility: Color-coded severity must not rely on color alone; alert tiles need semantic labels for unread/critical status.
  • Assessment: Solid pattern, but duplicated severity/color logic is a maintenance risk.

ProfileScreen — profile tab

lib/src/features/profile/presentation/screens/profile_screen.dart (~5,838 lines)

  • Visual: SectionHeader-gated sections: Account, Safety & Emergency, Preferences, About. Edit profile, digital ID card (CustomPaint QR/barcode placeholders), security settings, emergency contacts, medical info, location sharing, safety check-ins, activity history.
  • Layout: Massive single file. Sections gated by authentication state (— but the app has no login, so the authenticated branch may be dead or inconsistent code).
  • Interaction: ~15 string-route pushes (e.g. context.push('/profile/edit')) mixed with typed AppRoutes; most editors stubbed "coming soon".
  • Functional: Inline providers (placesVisitedCountProvider, routesTakenCountProvider, userSafetyScoreProvider, etc.). Digital ID QR/barcode are CustomPaint placeholders (non-functional).
  • Assessment: Over-scoped and incomplete; the weakest screen in the app.

DigitalTwinScreen

lib/src/features/digital_twin/presentation/screens/digital_twin_screen.dart

  • Visual: 3D WebView (Three.js) via webview_flutter. Floor selector (left), room search panel (right), room info panel (bottom), highlighted-rooms badge. Theme toggle (light/dark/emergency); exploded-view toggle.
  • Layout: Stack-based overlay on full-screen WebView; dense overlay UI.
  • Interaction: Room hover/select; floor change; fly-to-room; 300ms-debounced search.
  • Functional: Building3D model loading; coordinate transform; model loader service. "Navigate" button stubbed ("Coming soon").
  • Accessibility: WebView content is inaccessible to screen readers; color-coded room categories rely on color alone.
  • Responsiveness: Fixed-width panels (280px search, 60px floor selector) may break on small phones.
  • Assessment: Technically ambitious but accessibility-poor; 3D twin is secondary to core map navigation.

_MainShell — bottom navigation

lib/src/core/router/app_router.dart (inline)

  • Visual: Five destinations (Map, Navigate, Emergency, Alerts, Profile); Emergency tab highlighted in error color when selected; unread-alert badge on Alerts.
  • Layout: Connectivity banner above content. Custom InkWell-based nav items (comment references Material 3 NavigationBar but uses a custom build).
  • Interaction: Branch-based navigation via navigationShell.goBranch(index).
  • Accessibility: Nav items lack explicit semantics; badge is visual-only (no screen-reader announcement of count).
  • Responsiveness: Five tabs is at the upper limit for bottom nav on small phones; labels are 11px.
  • Assessment: Functional but custom-built rather than using Material 3 NavigationBar.

Theme & color system assessment

lib/src/core/theme/app_theme.dart and lib/src/core/theme/theme_provider.dart

Strengths

  • AppColors, AppTextStyles, AppSpacing, AppElevation, AppDurations — complete token system.
  • Inter + RobotoMono via Google Fonts — good sans + mono pairing for technical data.
  • Three ColorSchemes: light, dark, emergency. Emergency is a full-screen red emergency mode — appropriate for this app.
  • ThemeData builder with Material 3 component themes (elevatedButton, filledButton, outlinedButton, textButton, card, chip, bottomSheet, dialog, appBar, etc.).
  • Zoom / Cupertino page transitions — nice touch.
  • textScaler clamped 0.8–1.3 in _AppBuilder — good accessibility guardrail.
  • ThemeProvider with SharedPreferences persistence; AppThemeMode {system, light, dark, emergency}; emergency-mode toggle.

Weaknesses

  • Emergency ColorScheme can be activated independently of actual emergencies — potential for confusing UI state.
  • Several widgets use hardcoded Colors.red/Colors.green/Colors.blue/Colors.orange instead of theme color scheme (e.g. digital_twin_screen.dart, emergency badges in destination_details_bottom_sheet.dart). This breaks dark/emergency theme consistency.
  • _AppBuilder clamps text scaler but there is no evidence of large-text layout testing (text overflow at 1.3× scale).

Responsiveness & accessibility assessment

Responsiveness

  • Bottom sheets use DraggableScrollableSheet with min/max child sizes — good adaptive behavior.
  • Digital twin has fixed-width panels (280px search, 60px floor selector) — poor small-phone adaptation.
  • Bottom navigation has 5 tabs at 11px labels — crowded on small phones (<360dp width).
  • No evidence of breakpoint-based layout changes (no LayoutBuilder/MediaQuery adaptive patterns outside the map screen).
  • Map-screen FAB and bottom sheets may collide with bottom nav on small phones.
  • Verdict: Partially responsive; needs breakpoint-based adaptation and safe-area awareness.

Accessibility

  • Strengths: semanticLabel support on AppFilledButton, AppCard, AppChip, AppAvatar, EmptyState, LoadingOverlay, ErrorState, ErrorBanner; ExcludeSemantics on decorative icons; textScaler clamp (0.8–1.3); PopScope canPop:false on emergency status; liveRegion on loading/error semantics.
  • Gaps: map markers and FlutterMap layers have no screen-reader alternative; color-coded severity (alerts, destination types, room categories) relies on color alone; SOS hold has no documented haptic/audio fallback; bottom-nav badge is visual-only; Digital Twin WebView is inaccessible; instruction icons unlabeled.
  • Verdict: Good semantic infrastructure exists but is inconsistently applied. Map and Digital Twin are the biggest accessibility gaps.

Recommended redesign per screen

BeginScreen — keep as-is (visual/layout only)

The best-designed screen in the app. Keep the single-primary-action pattern. Consider adding a subtle campus wordmark or illustration for brand. No structural change needed.

MapScreen — map-first, consolidate bottom sheets

  • Keep full-screen map. Consolidate the 6 bottom sheet types into 2: a generic FeatureBottomSheet (building/room/pathway/marker) with a type-driven header chip, and a LayerOptionsSheet.
  • Unify handle bar, header, and action-button pattern across all sheets using shared EmptyState/LoadingState/ErrorState components.
  • Visual: Unified sheet header with type color from AppChip / ChipSeverity.
  • Functional/backend: No change to map layers or graph data.

NavigationScreen — extract duplicated helpers, finish stubs

  • Move Haversine + format helpers to a shared NavigationUtils class.
  • Replace "coming soon" voice search/guidance SnackBars with disabled states or remove until implemented.
  • Unify start-location mode selector with shared AppChip/AppSegmentedButton pattern.
  • Functional: Haversine moved to shared util (no behavior change).

EmergencyScreen — fix SOS auth contradiction, add fallbacks

  • Remove the userId/login requirement from _activateSos — SOS must work for any user in a no-login app. (Critical fix.)
  • Add haptic feedback and audio cues to the SOS hold; add a non-color indicator (text percentage) to the progress ring.
  • Visual: Emergency red theme retained; progress ring gets a text label.

AlertsScreen — centralize severity/color logic

  • Extract the 3 duplicated severity/color switch functions into a shared AlertSeverity helper (color + icon + label).
  • Use AppChip with ChipSeverity.emergency for critical alerts; ensure color is never the only indicator of severity (add text label + icon).
  • Backend: No change to Firestore streams or FCM.

ProfileScreen — split into feature files, remove stubs

  • Split profile_screen.dart (5,838 lines) into per-section screens, each in its own file under profile/presentation/screens/: EditProfileScreen, DigitalIDCardScreen, SecuritySettingsScreen, EmergencyContactsScreen, MedicalInfoScreen, LocationSharingScreen, SafetyCheckinsScreen, ActivityHistoryScreen.
  • Remove or gate all "coming soon" stubs; replace string-route pushes with typed AppRoutes; make Digital ID QR/barcode functional or remove.
  • Functional: Remove dead authenticated/unauthenticated branching if no login exists.

DigitalTwinScreen — make accessible, responsive

  • Replace fixed-width panels with responsive width (percentage-based or LayoutBuilder).
  • Add a non-3D fallback view (2D floor-plan list) for users who cannot use WebView; add room-category labels alongside icons/colors.
  • Backend: 3D model loading unchanged.

_MainShell — consider Material 3 NavigationBar

  • Evaluate replacing the custom InkWell nav with Material 3 NavigationBar, or keep custom but add semantics labels and screen-reader announcement for the badge.
  • Consider merging Alerts into Profile or Map to reduce to 4 tabs if 5 feels crowded.

Suggested reusable design system

Foundation layer (build first)

  1. Theme tokens — already exists in app_theme.dart (AppColors, AppTextStyles, AppSpacing, AppElevation, AppDurations). Lock it down; add a ThemeTokens class exposing ColorScheme-derived values so widgets never reference raw Colors.*.
  2. Color usage rule — no widget may reference Colors.red/Colors.blue/etc. directly; all color must come from Theme.of(context).colorScheme or AppColors.
  3. Component library — fix the material_ui/cupertino_ui import (replace with Flutter Material or remove); replace raw FilledButton/OutlinedButton in empty/error states with AppFilledButton/AppOutlinedButton.
  4. Navigation pattern — typed AppRoutes only; ban string-route pushes; centralize in app_router.dart.
  5. Bottom-sheet pattern — one AppBottomSheet wrapper with handle bar, header, action row; all feature sheets use it.
  6. Empty/error/loading pattern — use the shared EmptyState/ErrorState/LoadingOverlay consistently; no inline Center(child: Text(...)) fallbacks.

Phase-by-phase plan (starting with the shared design system)

Phase 1 — Shared design system (foundation)

Goal: Lock the design system so all later screen work is consistent.

  1. Fix the material_ui/cupertino_ui dependency (replace with Flutter Material or remove).
  2. Lock app_theme.dart tokens; add a ThemeTokens color accessor; ban raw Colors.* in widgets.
  3. Fix shared-widget-library inconsistencies (raw buttons → App* wrappers in empty/error states).
  4. Create shared utils: distance.dart (Haversine + format), instruction_icons.dart, alert_severity.dart.
  5. Create app_bottom_sheet.dart unified wrapper.
  6. Establish navigation rule: typed AppRoutes only; no string-route pushes.

Deliverable: A consistent, locked design system with zero raw-color references and no duplicated helpers.

Phase 2 — Critical fixes (P0)

Goal: Make the app functional and safe.

  1. Remove userId/login requirement from _activateSos in EmergencyScreen; add haptic/audio fallback.
  2. Remove or stub out the 8 missing router routes so navigation does not break.
  3. Make Digital ID QR/barcode functional or remove the feature.

Phase 3 — Core screens (P1/P2)

Goal: Bring Map, Navigate, Alerts to design-system standard.

  1. Consolidate map bottom sheets into FeatureBottomSheet + LayerOptionsSheet.
  2. Redesign NavigationScreen: extract duplicated helpers; replace "coming soon" stubs.
  3. Redesign AlertsScreen: centralize severity/color via AppChip/ChipSeverity; add non-color severity indicators.

Phase 4 — Profile & Digital Twin (P3)

Goal: Complete or de-scope incomplete features.

  1. Split profile_screen.dart into per-section screens; remove "coming soon" stubs; replace string routes with AppRoutes.
  2. Redesign DigitalTwinScreen: responsive panels, 2D fallback, accessibility labels.

Phase 5 — Accessibility & responsiveness (P4)

Goal: WCAG-aligned, adaptive experience.

  1. Map screen-reader alternatives; Digital Twin 2D fallback (already done).
  2. Color-not-only severity indicators; SOS haptic/audio (already done).
  3. Bottom-nav semantics + badge announcement.
  4. Breakpoint-based layouts; small-phone nav (4 vs 5 tabs).
